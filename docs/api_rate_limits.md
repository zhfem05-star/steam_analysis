# Steam API 요청 한도와 요청률 기준

2026-11-23 정리. Steam은 Web API 요청 한도를 공개하지 않으므로 직접 측정한 값과 실제 운영 기록으로 요청률을 정한다.
수집 주기와 데이터는 [collection_spec.md](collection_spec.md) 참고.

## 1. 요약

| API | 용도 | 현재 요청률 | 근거 | 429·차단 기록 |
|---|---|---|---|---|
| `ISteamUserStats/GetNumberOfCurrentPlayers` | 동접자 개별·스캔 | 초당 5건 (token bucket) | 초당 40건까지 429 없음 (11-18 측정)의 1/8 | 없음 |
| `ISteamChartsService/GetGamesByConcurrentPlayers` | 동접자 top 100 | 매시 1회 | 호출 수가 적어 측정 불필요 | 없음 |
| `IStoreService/GetAppList` | 게임 목록 | 페이지 사이 0.5초, 하루 5회 | 기본 간격 | 없음 |
| `IStoreQueryService/Query` | KR 가격·리뷰 요약 | 페이지 사이 0.5초, 하루 202회 | 기본 간격 | 없음 |
| `IUserReviewsService/GetAppReviews` | 리뷰 상세 (on-demand 예정) | 페이지 사이 0.5초 | 기본 간격. 키 없는 요청은 공용 한도 | 없음 |
| `store/api/appdetails` | 게임 메타 (재구성 예정) | 요청 사이 1.5초, 단일 worker | 알려진 한도 5분 200건(초당 약 0.67건)에 맞춘 간격 | **2026-11-12 HTTP 403** |

- 요청 간격은 코드 상수로 관리: `plugins/hooks/steam_api.py` `_RATE_LIMIT_SEC = 0.5`, `plugins/operators/steam_app_details_to_s3.py` `_RATE_LIMIT_SEC = 1.5`, 동접자 DAG `rate_per_sec=5.0`

### 채택 값: 초당 5건

- 측정 최대치의 1/8. 시간당 18,000건, 하루 432,000건
- 상한을 찾지 못했으므로 측정값은 "한도"가 아니라 "이만큼은 안전했다"는 하한
- 11-18 측정은 60초 구간뿐이라 수 시간 지속 요청이나 일일 누적 한도는 확인하지 못함. 그래서 측정 최대치 근처를 쓰지 않음
- 11-18 측정 대상은 인기 게임 1개(730)뿐. 서로 다른 게임 연속 조회는 아래 11-23 측정으로 확인

### 지속 부하 측정 (2026-11-23)

매시 수집 대상 확대(할인 이벤트 게임 추가 등)에 대비해 "20분 안에 개별 호출 12,000건"이 가능한지 확인

| 항목 | 값 |
|---|---|
| 대상 | 서로 다른 게임 12,000개 (관리 목록 중 리뷰 수 많은 순) |
| 방식 | 초당 10건 공유 token bucket, 동시 worker 4개 |
| 중단 조건 | 403 1회, 429 연속 3회 또는 누적 5회 |
| 시작 | 2026-11-23 11:54 UTC |

| 결과 | 값 |
|---|---|
| 요청 | 12,000건 전부 완료, 중단 없음 |
| 소요 | 1,208.6초 (약 20분 9초) |
| 실제 초당 | 9.93건 (분당 569~600건) |
| 응답 | HTTP 200 12,000건, 429 0건, 403 0건, 네트워크 오류 0건 |
| 응답 시간 | 중앙값 0.196초, p95 0.315초, 최대 2.216초 |

- 초당 10건 20분 지속, 서로 다른 게임 조회에서도 제한 없음 확인
- 응답 시간 중앙값 약 0.2초라 단일 순차 호출로는 초당 5건이 한계. 초당 10건은 동시 호출 2개 이상 필요
- 대상이 모두 인기 게임이라 데이터 없음(404) 응답은 0건. 실제 매시 수집과 같은 조건
- 측정 스크립트는 저장소에 넣지 않음. `scripts/probe_current_players_rate_limit.py`는 게임 1개 고정이라 다수 게임 측정이 필요하면 옵션 추가

- 서로 다른 게임을 초당 5건으로 조회해도 문제 없음을 확인. 2절의 캐시 우려는 이 범위에서는 해당 없음

### 차단 사례: appdetails 403 (2026-11-12)

- 당시 리뷰·앱 상세 수집 중 `store/api/appdetails`가 HTTP 403을 반환. 요청 폭주에 따른 일시 제한으로 판단
- 다음 날(2026-11-13) 자연 해소
- 병렬 요청이 403을 유발해 단일 worker 순차 실행으로 변경. 1.5초 간격은 5분 200건 한도와 같은 요청률
- `store.steampowered.com` 계열(appdetails)은 `api.steampowered.com` 계열(동접자 초당 40건 무오류)보다 한도가 훨씬 낮음
- 같은 날 리뷰 수집 실패는 별개 원인 (`/appreviews` 폐기, `GetAppReviews`로 이전)

## 4. 하루 요청량 (현재 설정 기준)

| 작업 | 1회 요청 | 하루 횟수 | 하루 요청 |
|---|---|---|---|
| 매시 동접자 | top 100 1회 + 개별 최대 약 2,100회 (예산 2,000 + 고정 대상 중 top 100 밖) | 24 | 최대 약 50,000 |
| 동접자 스캔 | 최대 30,000회 | 1 | 30,000 |
| 게임 목록 | 5회 | 1 | 5 |
| 가격 | 202회 | 1 | 202 |
| 합계 | | | 최대 약 80,000 |

- 매시 개별 2,100회는 초당 5건 기준 약 7분
- 스캔 30,000회는 약 100분 (21:00 ~ 22:40 UTC)

### 동시 실행 구간

- token bucket은 task 실행마다 따로 생성되어 DAG 사이에 공유되지 않음
- 스캔이 도는 21:00 ~ 22:40 UTC에는 21:00·22:00 매시 수집과 겹쳐 동접자 API를 최대 초당 10건 호출
- 측정 무오류 범위(초당 40건) 안이라 현재는 허용. 예산 N이나 요청률을 올릴 때는 합산 요청률로 판단

## 5. 429·차단 대응 규칙

| 상황 | 동작 | 위치 |
|---|---|---|
| 429 (동접자) | `Retry-After`만큼 대기 (없으면 60초) 후 요청률 절반, 최저 초당 0.5건 | `plugins/utils/rate_limit.py` |
| 연속 429 3회 초과 (동접자) | 실행 중단, manifest 미기록 → Slack 알림 | 같은 파일 `RateLimitedCaller` |
| 개별 호출 연속 실패 20회 또는 실패율 20% 초과 | 실행 중단, manifest 미기록 | `plugins/operators/steam_players_to_kafka.py` |
| 429 (그 외 API) | `SteamRateLimitError`로 task 실패 | `plugins/hooks/steam_api.py` |
| 403 등 그 외 오류 응답 | `requests.HTTPError`로 task 실패 | 같은 파일 |

- 차단 의심 응답을 받으면 재시도로 밀어붙이지 않고 멈추는 것이 원칙. 403은 하루 단위로 풀린 사례가 있어 재시도보다 다음 실행을 기다림
- 되돌리기 전 리뷰 수집에 있던 "403·429·리다이렉트·비JSON 응답 시 남은 요청 중단, 부분 결과 저장" 규칙은 현재 코드에 없음. on-demand 리뷰·앱 상세 재구성 때 다시 넣을 것

## 6. 요청률을 바꿀 때

- 동접자 요청률·예산은 DAG 인자 `rate_per_sec`, Airflow Variable `player_watchlist_budget`·`player_scan_max_per_run`으로 조정
- 올리기 전 확인
  - 4절 합산 요청률이 측정 무오류 범위(초당 40건)의 절반 이하인지
  - 매시 개별 호출이 45분 안에 끝나는지 (늦은 실행 차단 기준)
- 초당 10건(20분에 12,000건)은 2026-11-23 지속 측정으로 확인. 올릴 때는 producer를 동시 호출 구조로 바꿔야 함 (현재 단일 순차 호출이라 응답 시간 때문에 초당 약 5건이 상한)
- 매시 수집 상한 기준 (재시도 2회 여유 = 20분 안에 완료)
  - 초당 5건: 개별 호출 약 6,000건
  - 초당 10건: 개별 호출 약 12,000건
- 초당 10건 이상이 필요하면 장시간(예: 1시간 이상)·다수 게임 시나리오를 먼저 측정

## 7. 동시 호출 전환 (보류)

2026-11-23 결정: 매시 수집 대상이 399개라 현재 단일 순차 호출(worker 1개)로 충분. 설계만 남기고 구현은 보류

### 전환 시점

- 매시 개별 호출 수가 약 5,000건(초당 5건 기준 약 17분)을 넘을 때
- 예정된 확대 요인: 할인 이벤트 게임 동접자 별도 수집, 예산 N 상향, 고정 대상(top 100 진입 이력) 누적

### 목표 설정

| 항목 | 값 | 근거 |
|---|---|---|
| 요청률 | 초당 10건 | 11-23 지속 측정 (12,000건, 20분, 429 0건) |
| worker | 4개 | 필요 worker = 요청률 × 응답 시간. 중앙값 0.196초면 2개, p95 0.315초면 약 3개라 여유 포함 4개 |
| burst | 1 | 토큰을 쌓아 두지 않아 worker 수와 관계없이 0.1초 간격으로 1건씩 송신 |

- worker 수는 요청률을 올리지 않음. 요청률 상한은 token bucket이 정하고, worker는 느린 응답이 있어도 요청률을 유지하는 역할
- 동시 연결 수 자체는 11-18 측정(동시 8개, 초당 40건, 1분)과 11-23 측정(동시 4개, 20분)에서 문제 없음

### 구현 시 해결할 동시성 문제

| 문제 | 해결 |
|---|---|
| 같은 게임 중복 호출 | 게임 ID를 큐 또는 `ThreadPoolExecutor`에 한 번씩만 제출. 꺼내기는 라이브러리가 원자적으로 처리 |
| 토큰 상태 동시 수정 | `TokenBucket`의 다음 토큰 시각 계산과 `slow_down`·`pause`를 하나의 lock 안에서 처리 |
| 429·실패 집계 동시 갱신 | `RateLimitedCaller`의 연속 429 횟수, producer의 연속 실패·실패율 집계도 같은 lock으로 보호 |
| 429 수신 시 일부 worker만 대기 | `pause`가 버킷 전체에 적용되어 모든 worker가 함께 대기 |
| 중단 조건 도달 | 중단 신호(`threading.Event`)로 남은 요청 송신 중지 |
| Kafka 발행 | worker는 API 호출만 담당. 결과는 메인 스레드가 모아 기존처럼 200건 단위로 발행·flush |

- 중복 방지 장치는 이미 있음: producer `seen` 집합, Silver appid 중복 제거, DB 키 `(app_id, collected_at)` 덮어쓰기. task 재시도로 같은 게임을 다시 호출해도 같은 슬롯을 덮어쓸 뿐 행이 늘지 않음
- 테스트: 가짜 clock·가짜 API로 worker 4개에서 요청 간격 0.1초 유지, 429 시 전체 대기·요청률 절반, 게임별 1회 호출을 오프라인으로 검증
