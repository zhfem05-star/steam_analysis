# 성능 수치 근거 점검

점검일: 2026-10-16. 저장소 작업 트리와 남아 있는 로컬 task 로그를 확인했다. 과거 성능을 새로 측정하지 않았으며, 삭제된 실험 스크립트 복원이나 대량 재수집은 수행하지 않았다.

## 제출 문구의 현재 판단

- **약 2GB → 800MB:** 원본 측정 기록 미확인. 프로세스 RSS인지 컨테이너 메모리인지, peak인지 순간값인지, GB/MB와 GiB/MiB 중 어떤 단위인지 확정하지 못했다. 약 60% 감소를 검증된 성과로 확정하지 않는다.
- **수집 6,140초 → 5,000초:** 같은 입력·필터·시작 체크포인트·성공 ID 집합을 사용한 전후 기록 미확인. 약 18.6% 단축은 제시된 수치의 산술 결과이며 이번 로그 점검으로 입증한 성능 개선율이 아니다.
- **DB 적재 210초 → 18초:** 대상 테이블·입력 행 수·SQL 방식·트랜잭션·측정 구간을 특정할 원본 기록 미확인. 약 91.4% 단축을 현재 운영 코드의 검증된 성능으로 확정하지 않는다.
- **500 → 5,800 rows/s:** 처리량 산정에 사용한 성공 행 수와 시간 구간 미확인. 11.6배는 제시된 수치의 산술 결과이며 현재 코드의 측정 결과가 아니다.

미확인은 성과가 없었다는 뜻이 아니다. 저장소 밖의 당시 측정표·화면 캡처·실험 결과가 제공되면 조건을 확인해 다시 판단한다. 우선 제출본에서는 확인된 구현 방식으로 표현한다.

2026-10-16 본인 설명: 청크·yield 적용 이전에 CLI의 컨테이너 상태 화면에서 Airflow scheduler 메모리가 약 2GB를 점유한 것을 관측했으며 캡처는 남아 있지 않다. 정확한 명령은 기억하지 못한다. `docker ps`에는 메모리 지표가 없으므로 `docker stats`였을 가능성이 있지만 도구를 확정하지 않는다. 개선 후 800MB의 원본 관측값과 동일 조건 비교는 여전히 미확인이다. 포트폴리오에는 필요 시 “개발 중 scheduler 컨테이너의 높은 메모리 사용을 관측해 수집 방식을 개선”한 경험으로 설명하고 수치화된 감소율은 보류한다.

## 확인한 범위와 방법

- `docs/`, README, PIPELINE, `scripts/`, 테스트 코드와 성능·측정 파일명 후보를 확인했다. 해당 수치의 측정표나 전용 benchmark 결과 파일을 발견하지 못했다.
- `logs/dag_id=*/**/*.log`의 task 로그 576개를 읽었다. 이 중 371개 파일에서 `Marking task as SUCCESS`와 시작·종료 시각을 함께 찾았다. 나머지를 모두 실패로 분류한 것은 아니다.
- 성공 종료 로그의 `start_date`와 `end_date` 차이로 task 경과 시간을 계산했다. 이 값은 초 단위 기록이며 순수 API 시간이나 DB 실행 시간과 같지 않다.
- 6,140/5,000초 및 210/18초 주변 실행도 확인했지만, 비슷한 시간이 나왔다는 이유로 원래 측정과 연결하지 않았다.
- 로그에 배포 Git 해시가 없어 과거 실행을 특정 커밋과 확정적으로 연결하지 않았다. 현재 코드의 테스트 통과를 과거 수치의 증거로 사용하지 않는다.

## 현재 사용할 수 있는 표현과 다음 확인

확인된 구현을 설명하는 문구 후보:

> 리뷰 수집을 페이지 큐와 청크 저장 구조로 개선하고, 게임별 병렬 수집과 Parquet 저장을 적용했다. 후속 버전에서는 Kafka·Spark 기반 적재와 날짜 체크포인트 재개를 구현하고 소량 통합 테스트로 검증했다.

> Silver 적재의 다중 행 파라미터 전달 문제를 수정하고, 명시적 트랜잭션과 executemany를 적용했다.

위 문구의 개인 기여 범위는 본인이 최종 확인한다. 수치 근거가 확인되기 전에는 메모리 감소율·시간 단축률·처리량 배수를 붙이지 않는다.

기존 자료를 추가로 확인할 때 필요한 최소 정보:

- 메모리: 측정 도구, 프로세스/컨테이너 대상, peak/순간값, 원본 단위, 동일 입력과 동시 작업 수
- 수집: 전후 버전, 게임·언어·필터, 시작 cursor, 수집·고유 ID 수, API 요청 수, 측정 시작·종료 지점
- DB: 대상 테이블과 스키마, 고정 입력 행 수, 전후 SQL·드라이버·트랜잭션 방식, 성공 행 수, commit 포함 여부, 반복 횟수

자료가 없으면 기존 수치는 보류하고 P0 제출 문구부터 확정한다. 재측정은 별도 실험으로 기록하며 과거 결과를 복원한 것으로 표현하지 않는다.

## 2026-10-16 새 DB 호출 방식 측정

과거의 `210초 → 18초` 또는 `500 → 5,800 rows/s`를 재현한 실험이 아니다. 현재 Docker 환경에서 동일 입력에 대한 호출 방식 차이를 새로 측정했다. 운영 코드에는 반영하지 않았다.

- 실행 코드: [profile_review_db_writes.py](../scripts/profile_review_db_writes.py)
- 원본 표본·환경·스크립트/입력 SHA-256: [측정 JSON](evidence/review_db_write_profile_20261016.json)
- 실행 경로: Airflow scheduler 컨테이너 → 실제 analytics-postgres 연결. 고정 입력 10,000행, 각 방식 5회, 방식별 100행 이하 예열, 실행 순서 로테이션.
- 동일한 기본 키와 `ON CONFLICT DO UPDATE` SQL 의미를 사용하되 매회 테이블을 비워 **신규 INSERT 경로**만 측정했다. 기존 행 충돌 UPDATE 성능은 측정하지 않았다.
- 방식별 트랜잭션은 모두 1회다. 행마다 commit하는 방식은 비교하지 않았다.
- 타이머에는 호출 루프/값 직렬화, SQL 실행, 마지막 commit을 포함한다. 연결 생성, 입력 생성, 테이블 준비·TRUNCATE와 결과 검증은 제외한다. 각 실행 후 전체 결과 10,000행이 원본 튜플 목록과 일치하는지 검증했다.
- 세션 전용 PostgreSQL TEMP 테이블을 사용했다. 영구 테이블의 데이터 WAL·복제·디스크 내구성 비용을 반영하지 않으므로 운영 테이블의 절대 시간·처리량으로 일반화하지 않는다.

실측 결과(5회 중앙값):

- 행별 `cursor.execute`: **1.920549초**, 약 **5,207 rows/s**. 표본 범위 1.866074~2.028755초.
- `cursor.executemany`: **1.927902초**, 약 **5,187 rows/s**. 표본 범위 1.867695~2.126001초. 현재 코드와 같은 드라이버 호출 방식이며 이번 조건에서는 행별 execute와 차이가 거의 없다.
- `psycopg2.extras.execute_values`, 페이지당 1,000행: **0.253402초**, 약 **39,463 rows/s**. 표본 범위 0.248474~0.276968초.

`execute_values`의 중앙값은 행별 execute 대비 약 **7.58배 처리량**, 약 **86.8% 시간 감소**다. 이 수치는 위 TEMP 테이블의 고정 입력 실험에만 적용하며 과거 성과나 현재 운영 파이프라인 개선율로 표현하지 않는다. 실제 적용은 후속 선택 사항이다.

```sh
docker exec airflow-scheduler env PYTHONPATH=/opt/airflow/plugins python /opt/airflow/scripts/profile_review_db_writes.py --rows 10000 --repeats 5 --output /opt/airflow/logs/review_db_write_profile_20261016.json
```

사용 가능한 새 실험 설명:

> 실제 PostgreSQL 연결에서 동일한 1만 행을 세 가지 호출 방식으로 각각 5회 측정했다. 단일 트랜잭션 TEMP 테이블 조건에서 executemany와 행별 execute는 비슷했고, execute_values의 중앙값은 1.92초에서 0.253초로 줄었다. 이를 후속 개선 후보로 확인했으며 운영 코드에는 아직 적용하지 않았다.
